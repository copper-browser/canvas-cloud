# canvas-cloud v0.1.0

The first release of canvas-cloud: a self-hostable server for real-time collaborative
canvases. One Rust binary and a PostgreSQL database give people shared whiteboards they edit
together live (Yjs over `y-websocket`), give agents a REST and MCP interface to read and draw
on them, and let other services link to the server with an app key so their users get
canvases without a second account. MIT licensed.

## What is in it

**Canvases** ([canvas.md](canvas.md), [canvas-protocol.md](canvas-protocol.md))

- A Personal canvas per user and shared canvases with owner/editor roles, email invites,
  share links (`/join/{token}`) and a people directory (the people you share canvases with,
  or a linked app's own users).
- Live rooms speaking the standard `y-websocket` protocol (HTTP/1.1 upgrade or HTTP/2
  extended CONNECT); every update is written to PostgreSQL before it is broadcast; snapshots
  compact the update log every 200 updates.
- An agent-friendly read format (`GET /v1/canvases/{id}/read`) and validated ops
  (`POST /v1/canvases/{id}/ops`) applied to the live document.
- Canvas chat in the document, with @mention notifications (`/v1/mentions`).
- Encryption at rest: a key per canvas, wrapped by the server's master key; updates,
  snapshots and mention excerpts are AES-256-GCM sealed.

**People and sign-in** ([auth.md](auth.md), [events.md](events.md))

- Password accounts (Argon2id) with a signup policy: the first account is open, then
  `allow_signup` and optional `signup_domains`.
- Sign-in with any OpenID Connect provider (authorization code + PKCE).
- Personal access tokens with `read` or `write` scope, for scripts and agents.
- `GET /v1/events`: a per-user server-sent event stream with `Last-Event-ID` resume.
- A built-in `/account` page: sign in, manage access tokens, connect an agent.

**Linked apps** ([apps.md](apps.md), [import-format.md](import-format.md))

- Another service registers once (`canvas-cloud apps create`) and acts for its own users with
  an app key and `X-Canvas-User`: user provisioning (single and batch), an app-wide event
  stream, canvas listing, stats, digests, and import format v1 (NDJSON) to bring canvases
  over from another system.

**Agents** ([agents.md](agents.md), [openapi.md](openapi.md))

- An MCP server at `POST /mcp` (Streamable HTTP, protocol `2025-06-18`, stateless) with tools
  to list, read and edit canvases, members and mentions; `GET /llms.txt`; an OpenAPI 3.1
  document at `GET /v1/openapi.json`.

**Operations** ([install.md](install.md), [configuration.md](configuration.md),
[operations.md](operations.md))

- TLS built in: self-signed (with a pinnable fingerprint), Let's Encrypt (TLS-ALPN-01), or off
  behind a reverse proxy.
- A one-command installer for systemd Linux (native PostgreSQL, a sandboxed unit, upgrades
  by re-running it). It can install for a reverse proxy or a loopback-only listener
  (`CANVAS_CLOUD_LISTEN`, `CANVAS_CLOUD_TLS_MODE=off`) and has a `--dry-run`.
- `canvas-cloud doctor`, Prometheus metrics, JSON logs, a CLI for accounts, signup policy and
  linked apps.
- Optionally serves a built canvas web app from `web_root` on the same origin.

Release binaries: Linux `x86_64` and `aarch64` (glibc 2.28 or newer), with `SHA256SUMS`.

## Compatibility

From this release on, these are the stable contract with clients:

- the canvas REST API under `/v1` (routes, request and response JSON, status codes and error
  codes);
- the WebSocket protocol: `y-websocket` framing, the document schema and the close codes;
- the ops and read formats, import format v1, and the event stream frames.

Later releases may add routes, fields, ops, shape types, event kinds and features (listed in
`GET /v1/info` → `features`); clients should ignore what they do not know. Removing or
changing the meaning of anything above is a breaking change: before 1.0 it only ships in a new
minor version (0.2, 0.3, …) and is listed under **Breaking** in the [changelog](../CHANGELOG.md).

Not covered: the Rust crate APIs (internal), metric names, CLI output, and log fields.
Database migrations only go forward; a downgrade across a migration needs the backup taken
before the upgrade ([operations.md](operations.md#upgrades-and-migrations)).

## Known limitations

- **Single process per database.** Live rooms and the event buffer are in memory, so two
  processes on one database would not see each other's live edits. Scale up, not out.
- **Events are kept in memory only** (the last 4096). After a restart, or for a client that
  fell further behind, the stream sends `resync` and the client re-reads state. There is no
  integration test for the `lagged` resync path (its parts are unit-tested).
- **OIDC has only been tested against an in-process mock provider** over loopback HTTP, not
  against a real provider over TLS. Try a sign-in with your provider before relying on it.
- **No master-key rotation.** Changing `master_key` makes every stored canvas unreadable; back
  the key up.
- **Revoking access does not cut open WebSockets** when done from the CLI (`admin users
  disable`, `set-password`) or by revoking a session or token: an open room connection stays
  until it reconnects. Restart the service to cut them at once. (Removing a member, deleting
  a canvas, and a linked app's disconnect call close sockets at once.)
- **No outgoing email.** Invites are recorded and announced through events; delivering them
  is up to a client or linked app.
- **No path prefix.** The server must own the root of its origin.
- **No admin role in the HTTP API.** Administration is the CLI on the host.
- **Binaries for Linux only.** Other platforms build from source.
